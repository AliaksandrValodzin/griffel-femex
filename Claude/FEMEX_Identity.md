# Round-trip identity — the integer id stays the key, a GUID says "this is the same object"

> **Step 0 (repo convention):** this document sits alongside `Claude/FEMEX.md`, `Claude/FEMEX_Plates.md`,
> `Claude/FEMEX_Node_Sharing.md`, `Claude/FEMEX_Gridlines.md`, `Claude/FEMEX_LoadCombinations.md`,
> `Claude/FEMEX_BarLocalAxes_LoadDirection.md` and `Claude/FEMEX_SelfWeight.md`;
> `Claude/FEMEX_Identity_Summary.md` records what was actually built.

## Context

`Claude/FEMEX_Assessment.md` §4 item 6 and `Claude/FEMEX_Interop_Review.md` table 2.2 row
**"Round-trip identity"** name the same P0 gap. Every program in the comparison has a stable per-object
handle that survives leaving and re-entering it — Robot's name-keyed labels, Revit's `UniqueId`, ETABS'
object GUIDs, RFEM's integer `no`, SAF's optional `Id` column whose *documented purpose* is exactly this.
FEMEX has none.

The failure is not a lost number, it is a **duplicated model**. Program A exports to FEMEX, an engineer
edits the file elsewhere, A re-imports it — and A has no way to know that the returning `"id": 7` is the
bar it exported. It cannot merge, so it appends. Second consequence: combining two FEMEX files today
requires an id remap on every single reference, because nothing stops two producers minting `1` for
different things.

Review §4.6 weighs GUID-as-primary — the direction `FEMEX_Assessment.md` decision 3 had locked in —
against what the five programs actually key on, and lands on SAF's answer instead. SAF had this exact
decision to make with every vendor in the room and chose **neither exclusively**: `Name` is the required,
human-readable cross-sheet reference key, `Id` is an *optional* UUID existing solely for round-trip
matching, and `Parent ID` is a third layer for derived objects. Three layers doing three different jobs,
and §1.6 of the review is explicit that it is not an accident.

**Outcome:** a FEMEX file can say "this object is the one you gave me", without a single existing
reference in the format changing, without the JSON becoming unreadable, and with the entities that Robot
and ETABS key *by name* warning when they have no name to be keyed by.

## The eight decisions

### 1. The integer id stays the in-file reference key

`Bar.StartNodeId`, `Plate.NodeIds`, `AreaLoad.PlateId`, `Hinge.ElementId` and every other reference are
untouched. This is what RFEM does too, and it is what makes the whole change additive rather than a
rewrite. Review §4.6 lists what GUID-primary would have cost: `"startNodeId": 101` becoming a 36-character
string, no natural ordering where node 1–100 on level 1 is a readable convention, roughly 5× growth on
every reference in a file already 108 KB, and every one of the 85 tests plus the hand-authored example
rewritten. It also would not have solved the Robot problem, because Robot's properties are keyed by *name*.

### 2. A new optional `Uid`, a canonical GUID

`Guid?`, serialized as the standard 36-character string, and — because
`DefaultIgnoreCondition = WhenWritingNull` is already set on `FemexModel.JsonOptions` — **omitted entirely
when null**.

Null is a truthful value, not a gap: it means "this object has no round-trip identity", which is the
honest state of a hand-authored file. A canonical `Guid` rather than an opaque string because that is
SAF's `Id` exactly, and because the parser then validates the shape for free. The cost is real and worth
stating: Revit's `UniqueId` is a GUID plus an eight-hex episode suffix and IFC's `GlobalId` is a 22-character
base64 compression, so neither drops in verbatim. SAF's own guidance is the answer — the **exporting**
application assigns the uid and remembers the mapping to its native handle. That is a translator's job,
not the format's.

### 3. Never minted automatically

A public `AssignMissingUids()` the caller invokes. It fills nulls and **never overwrites** — an existing
uid is the anchor, and rewriting it is the one thing that would destroy the feature.

`ToJson()` is left alone beyond its existing version stamp. Auto-stamping on save was considered: the
precedent exists, since `ToJson` already mutates `SchemaVersion`. It was rejected because the same model
built twice from the same source would then carry different uids, and `Examples/Example1.femex` could
never be regenerated byte-identically — the property that made the plate migration in `FEMEX_Plates.md`
checkable at all.

### 4. All authored entities carry it; the mesh does not

A mesh is regenerated wholesale, so a stable identity for a mesh node or face means nothing — and review
§3.4 already establishes the mesh as generated data rather than authorship. `MeshNode` and `MeshFace` are
therefore out.

`Gridline` is also excluded, for a different reason: its identity is already `Label`, non-nullable,
required by validation and unique per grid (`FemexModel.Validation.cs:138`), and no program keys a
gridline by anything else.

### 5. `Load` gains an integer `Id`

Loads are the only authored entity with no key at all today — list position and an optional label. A load
carrying a uid but no integer id would be the sole exception in the format, and a duplicate-uid message
would have nothing to name it by. `Load.Id` lives in its own space, beside `Support.Id` and `Hinge.Id`,
not in the shared element space, because a load is not an element.

### 6. Names get a warning, not a requirement

`Name`/`Label` stays `string?` on `Section`, `SurfaceProperty`, `Material` and `LoadCase` — the four
entities review §4.6 names as the ones Robot and ETABS key by name — and blank or duplicated raises a
**warning** worded for name-keying programs.

Two precedents were available. `Gridline.Label` is non-nullable and blank is an *error*;
`LoadCombination.Label` is nullable and blank is a *warning*, worded exactly for this problem
(`Validation.cs:833`: "a program that keys combinations by name will invent one"). The combination
precedent is the newer one, was written for this same class of program, and keeps every existing file
valid at error level. Review §4.6 wanted required; this is the half-step, and §"Still open" says so.

### 7. SAF's `Parent ID` is deferred

Its documented use is reconstituting a curved member that a receiver segmented into straight pieces, and
FEMEX's "curves as chords" decision (review §6) leaves nothing to reconstitute. Mesh faces already
back-link through `MeshFace.PlateId`. The FEMEX-shaped cases — a plate cut into several plates, a bar
split at an intersection node, a region promoted to its own plate — are real but have no reader yet, and
the repo's habit is not to add a second way of saying something nothing consumes.

### 8. Schema version bumps to 1.3

New fields appear and a 1.2 reader would drop them in silence, so the file genuinely is a different
format.

## What changes

### The `Uid` itself

New `IIdentified.cs` in the root namespace:

```csharp
/// <summary>
/// Something a receiving program can recognise on re-import as the object it
/// exported, rather than duplicating it. Null is a real answer, not a gap: it
/// says this object has no round-trip identity, which is the honest state of a
/// hand-authored file.
/// </summary>
public interface IIdentified
{
    Guid? Uid { get; set; }
}
```

Then `public Guid? Uid { get; set; }` on **thirteen declaration sites**, each implementing `IIdentified`,
declared immediately after that type's integer key so it reads second in the JSON:

| File | Covers |
|---|---|
| `Geometry/Element.cs` | `Bar`, `Plate` |
| `Geometry/PlateRegion.cs` | |
| `Geometry/Node.cs` | |
| `Geometry/Level.cs` | |
| `Geometry/Grids/Grid.cs` | |
| `Geometry/Sections/Section.cs` | `Rectangle`, `Circle`, `TSection` |
| `Geometry/Surfaces/SurfaceProperty.cs` | `ConstantThickness` |
| `Materials/Material.cs` | |
| `Loads/Load.cs` | `PointLoad`, `LinearLoad`, `AreaLoad`, `TemperatureLoad` |
| `Loads/LoadCase.cs` | |
| `Loads/Combinations/LoadCombination.cs` | |
| `BoundaryConditions/Support.cs` | |
| `BoundaryConditions/Hinge.cs` | |

On ordering: `Section`, `SurfaceProperty` and `Load` are polymorphic, and System.Text.Json writes derived
properties before base ones, so `uid` lands beside `id` at the *end* of those objects — exactly where
`name` already sits today (`Examples/Example1.femex:754`).

### `Load.Id`, and the 1.2 → 1.3 migration that keeps it honest

`Loads/Load.cs` gains `public int Id { get; set; }` above `Uid` and `Label`. The four load classes have no
public constructors — everything is object-initializer — so this is one added line at eight call sites in
the tests, not a signature change.

The trap: a pre-1.3 file read into the new type gives every load `Id = 0`, and the duplicate check would
then report a flood of errors on a file that was never wrong. The existing deserialize hook handles it.
`FemexModel.SelfWeight.cs:45` already routes `IJsonOnDeserialized.OnDeserialized()` to
`MigrateLegacyUnitWeight()`; `MigrateLegacyLoadIds()` goes beside it, gated on `SchemaVersion` being null,
`"1.1"` or `"1.2"` — all of which by definition have no load ids — and numbering the loads `1..N` in list
order, which is the only identity a pre-1.3 load ever had. It records what it did the way
`_migratedUnitWeightMaterialIds` does, so `Validate()` can report it.

Gating on the version rather than on "the id is 0" is deliberate: a 1.3 file is left alone, so genuinely
duplicated load ids in a current file are still an error.

### Model helpers — `FemexModel.Identity.cs` (new partial)

```csharp
public int AssignMissingUids()                          // fills nulls, never overwrites; returns the count
private IEnumerable<(IIdentified Entity, string Owner)> EnumerateIdentified()
```

`EnumerateIdentified()` is the single list of what carries a uid, and **both** `AssignMissingUids()` and
the validator read it — the same "stated once so they cannot disagree" discipline as
`GetCoincidenceTolerance()` shared between `FindNodeAt` and the validator (review §3.8), and as
`GetEffectiveProperties` shared between validation and the self-weight helpers. `Owner` is the wording the
existing messages already use: `"Material 3"`, `"Bar 12"`, `"Plate 4 region 2"`, `"Load 7"`.

### Validation — `FemexModel.Validation.cs`

**Errors.** In `ValidateDuplicateIds`, one line beside the twelve already there:

```csharp
foreach (var m in ReportDuplicates(Loads.Select(l => l.Id), "load id")) yield return m;
```

New `ValidateUids(ctx)` in the error block:

- **A uid naming two objects** — `Uid 3f2a… names both Material 1 and Bar 12; a uid names one object.`
  Uniqueness is **model-wide**, not per collection: that is what a GUID means, and a receiver merging by
  uid does not care which list an object came from.
- **The nil uid** (`Guid.Empty` written explicitly) — it is the "I forgot" value, not an identity.

**Warnings.**

- **Partial coverage**, one message model-wide, silent for the two normal states (none carry a uid, all
  do): `12 of 47 authored objects carry a uid; a receiving program merges those and duplicates the rest.`
- **Names**, new `ValidateNameKeys(ctx)` over `Section`, `SurfaceProperty`, `Material` and `LoadCase`,
  reusing the exact two-message shape of `ValidateLoadCombinationUsage` (`Validation.cs:833`) — one for a
  blank name, one per duplicated name with the *name* as the subject, so three colliding entries produce
  one message rather than three.
- **The migration report** — generalise `ReportUnitWeightMigration()` to cover both migrations, adding
  `This model was written before loads had ids; its 109 loads have been numbered 1–109 in list order.`

### Schema version — `FemexModel.cs`

`CurrentSchemaVersion` → `"1.3"`; `ReadableSchemaVersions` → `{ "1.1", "1.2", CurrentSchemaVersion }`; the
`SchemaVersion` doc comment gains the 1.3 line.

`ValidateSchemaVersion()` needs a `"1.2"` branch. Its comment currently frames itself as "the three cases
`ReadableSchemaVersions` allows"; that becomes four. The 1.2 message says only what is true of a 1.2 file
— nothing in it carries a round-trip id — while the load-numbering fact is reported once by the migration
report above rather than duplicated into both the 1.1 and 1.2 branches, because the repo never reports one
fact twice (`Validation.cs:704`).

### `Examples/Example1.femex`

- `schemaVersion` → `"1.3"`.
- `"id": n` added to each of its **109 loads**, numbered in list order — the same numbering the migration
  produces, so the shipped file is exactly what re-saving it yields.
- **No uids.** The file is hand-authored and has no producing application, so null is the truthful value.
  Adding uids to part of it would trip the partial-coverage warning, and adding them to all of it would
  wreck the hand-editability that review §4.6 explicitly counted as a cost of GUIDs. The feature is
  demonstrated in the tests and in the snippet above instead.

### Tests

`griffel-femex.Tests/SampleModels.cs` — add `Id = n` to its eight loads. Its sections, surface properties,
materials and load cases are all already named (`SampleModels.cs:132–154`), so the new name warnings do
not fire and `RoundTripTests.SampleModel_IsValid`'s `Assert.Empty(model.Validate())` — which asserts across
*all* severities — stays green.

Two existing assertions hard-code the version string and change to `1.3`: `LoadDirectionTests.cs:146` and
`SelfWeightTests.cs:197`.

New `griffel-femex.Tests/RoundTripIdentityTests.cs`:

- a uid survives serialize → deserialize, and a null uid writes no `"uid"` key at all;
- `AssignMissingUids()` fills only the nulls, returns the count, and leaves an existing uid untouched
  across a second call, which returns `0`;
- a duplicate uid across two *different* collections is an error; `Guid.Empty` is an error;
- partial coverage warns once; full and empty coverage are silent;
- blank and duplicated `Material` / `Section` / `SurfaceProperty` / `LoadCase` names each warn;
- a duplicate `Load.Id` in a 1.3 file is an error;
- a 1.2 JSON fixture (inline, as `SelfWeightTests.cs:107` does for 1.1) reads with its loads numbered
  1..N, reports the migration, and re-emits as 1.3;
- `Examples/Example1.femex` loads, validates with no errors, and re-serializes.

## Still open

- **`UnmappedMemberHandling` is still not set** on `FemexModel.JsonOptions` (`FemexModel.cs:108`), despite
  review §4.5 naming it alongside the version field. A 1.3 file read by a 1.2 build drops its uids in
  silence — the exact failure mode §4.5 calls disqualifying for an interchange format. Adjacent to this
  change and deserving its own pass; not folded in here because it would turn every forward-compatible
  read into a throw, and that is a policy decision of its own.
- **Robot's name-key is only half-served.** A warning tells an author their material has no name; it does
  not stop them shipping one. Review §4.6 wanted required, and decision 6 is the half-step.
- **`Parent ID` has no reader yet.** Deferred by decision 7; the moment FEMEX grows a splitting operation
  — a plate cut into several, a bar split at an intersection — it becomes real.
- **Nothing here tells a receiver what the uid *was*.** A translator holds the mapping from uid to its
  native `UniqueId` / GUID / label; the file does not. That is SAF's design and is almost certainly right,
  but it means a uid is only as good as the exporter's memory of it.
- **Merging two FEMEX files is still not implemented**, only made possible. Integer ids still collide; a
  merge helper that keys on uid and remaps the integers around it is the obvious next step and is not in
  this change.

## Verification

```
dotnet build
dotnet test          # 85 existing facts, plus the new RoundTripIdentityTests
```

End-to-end, beyond the suite:

1. Load `Examples/Example1.femex`, assert `Validate(ValidationSeverity.Error)` is empty.
2. Call `AssignMissingUids()`, save to a scratch path, reload, and assert every uid came back identical —
   the round trip the whole change exists for.
3. Call `AssignMissingUids()` again on the reloaded model and assert it returns `0`: nothing was
   overwritten.
4. Take the pre-change `Example1.femex` (schemaVersion 1.2, no load ids) from git, load it, and confirm
   its loads are numbered 1–109, the migration is reported, and no errors are raised.
