# Round-trip identity — Implementation Summary

Implemented `Claude/FEMEX_Identity.md` in full, all eight decisions as written. Clean build
(0 warnings, 0 errors); 211 tests pass (was 179).

The failure this removes is not a lost number, it is a duplicated model: program A exports to FEMEX,
an engineer edits the file elsewhere, A re-imports it — and A had no way to know that the returning
`"id": 7` was the bar it exported, so it appended rather than merged. A FEMEX file can now say "this
object is the one you gave me", and **not one existing reference in the format changed** to make it
possible.

## The shape of the answer

Three layers doing three different jobs, which is SAF's design and not an accident:

| Layer | Job | In FEMEX |
| --- | --- | --- |
| Integer id | this file's own references | unchanged — `Bar.StartNodeId`, `Plate.NodeIds`, `AreaLoad.PlateId`, `Hinge.ElementId` |
| Name | what Robot and ETABS key by | `string?`, blank or duplicated is a **warning** |
| Uid | "this is the object you gave me" | optional `Guid?`, omitted when null |

`FEMEX_Assessment.md` decision 3 had locked in GUID-as-primary. Review §4.6 priced it — every
reference growing 5× on a file already over 100 KB, no natural ordering, the example file's hand
surgery made materially harder, every test rewritten — and noted that it would still not have solved
the Robot problem, because Robot's properties are keyed by *name*. The middle path buys the
round-tripping without any of that, and is what the interop review's `Closed by` blockquote now
records.

## Two things the design turns on

**Null is a value, not a gap.** `DefaultIgnoreCondition = WhenWritingNull` was already set, so a null
uid writes no key at all. `Example1.femex` therefore carries none, which is the truthful state of a
hand-authored file with no producing application — and it costs the file nothing to say so.

**Nothing mints a uid automatically.** `AssignMissingUids()` is a call the caller makes; it fills nulls,
returns the count, and never overwrites. Auto-stamping on save had a precedent — `ToJson()` already
mutates `SchemaVersion` — and was rejected anyway: the same model built twice from the same source
would carry different uids, and `Example1.femex` could never be regenerated byte-identically, which is
the property that made the plate migration checkable at all.

`EnumerateIdentified()` is the single statement of what carries a uid, and `AssignMissingUids()` and
both validators read it, so they cannot disagree about the set — the same discipline as
`GetCoincidenceTolerance()` shared between `FindNodeAt` and the validator, and `GetEffectiveProperties`
shared between validation and the self-weight helpers.

## Validation

Three errors:

```
Duplicate load id 4.
Uid 6c4f… names both Bar 1 and Material 1; a uid names one object.
Material 1 carries the nil uid 00000000-0000-0000-0000-000000000000, which is the value meaning
"not set" rather than an identity. Omit the uid instead.
```

Uid uniqueness is **model-wide**, not per collection: that is what a GUID means, and a receiver merging
by uid does not care which list an object came from. The integer id spaces are untouched — a load id
may equal a plate id, and `LoadId_IsInItsOwnSpace` pins that.

Four warnings:

```
44 of 45 authored objects carry a uid; a receiving program merges those and duplicates the rest.
Material 1 has no name; a program that keys materials by name will invent one.
More than one section is named "R300x500". A program that keys sections by name cannot tell them apart.
This model was written before loads had ids; its 83 loads have been numbered 1–83 in list order.
Re-saving the model writes those ids.
```

Coverage is one message model-wide and silent for both normal states — none carry a uid, all do —
because the fact is about the file, and a partly-stamped model of a thousand objects would otherwise
bury every other message. The two name messages reuse the exact shape of
`ValidateLoadCombinationUsage`: one per blank name, one per *duplicated name* rather than per colliding
entry, so three sections sharing a name produce one message. A blank name is never also a duplicate —
an absent name is not a name three sections share.

## The 1.2 → 1.3 migration

`Load.Id` created a trap: a pre-1.3 file read into the new type gives every load `Id = 0`, and the new
duplicate check would report a flood of errors on a file that was never wrong. `MigrateLegacyLoadIds()`
runs from the existing `IJsonOnDeserialized` hook, numbers the loads 1..N in list order — the only
identity a pre-1.3 load ever had — and records the count for `Validate()` to report.

Gated on the **declared version**, not on "the id is zero". A 1.3 file is left exactly as it is, so a
genuinely duplicated load id in a current file is still an error; `A13File_IsLeftAloneByTheMigration`
is that fact. `A11File_IsMigratedTwice` pins that a 1.1 file gets both migrations, independently, from
the one hook.

## Deviations from the plan

1. **Three of the plan's counts were stale**, and the code is what they now say: the suite was 179
   tests, not 85; `Example1.femex` has **83** loads, not 109; `SampleModels` has **7**, not 8.
2. **`ValidateUids()` and `ValidateNameKeys()` take no `ValidationContext`.** The plan writes both as
   `(ctx)`; neither needs a lookup table — one reads `EnumerateIdentified()`, the other the four lists
   directly — and the parameter would have been dead. `ValidateGravity()` and `ValidateSelfWeight()`
   already take none.
3. **Partial coverage is its own `ValidateUidCoverage()`**, not part of `ValidateUids()`. `Validate()`
   groups by severity and wraps whole sequences, so an error validator cannot also yield a warning.
4. **`ReportMigrations()` moved out of `ValidateSelfWeight()`** into `Validate()`'s warning block, next
   to `ValidateSchemaVersion()`. Generalising it as the plan asks makes it no longer a self-weight
   fact; the two now read as the pair they are — what the file says it is, and what reading it did.
5. **`MigrateLegacyLoadIds()` lives in `FemexModel.Identity.cs`**, not beside `MigrateLegacyUnitWeight()`
   in `FemexModel.SelfWeight.cs`. Only the `OnDeserialized` hook is shared; load ids have nothing to do
   with self-weight, and the unit-weight conversion is in that file precisely because it needs the
   gravity arithmetic next to it.
6. **The "no load case carries self-weight" warning gained a 1.2 case** — not in the plan, but forced
   by it. That check was gated on `SchemaVersion == CurrentSchemaVersion`, so bumping the constant to
   1.3 would have silently stopped asking a 1.2 file a question that 1.2 can answer: self-weight is the
   feature 1.2 *added*. The gate now names the versions in which self-weight exists.
7. **Seven tests beyond the plan's list**, each pinning something the plan states in prose:
   `ToJson_NeverMintsAUid` (decision 3), `Uid_IsCarriedByEveryAuthoredEntity_AndByNoMeshObject`
   (decision 4, both halves), `TheNilUid_IsNotAlsoReportedAsADuplicate`, `ABlankName_IsNotAlsoADuplicate`,
   `Warns_OnceForThreeSectionsSharingAName`, `ANameIsOnlyEverAWarning` (decision 6's half-step),
   `A11File_IsMigratedTwice`, and `Example1_ReSerializesToItself`.

## Verified

- `dotnet build`: 0 warnings, 0 errors. `dotnet test`: 211 passed, 0 failed.
- `Assert.Empty(SampleModels.Build().Validate())` still holds across all severities: the fixture's
  sections, surface properties, materials and load cases were already named, so no name warning fires,
  and nothing in it carries a uid, so coverage is silent.
- **`Example1.femex` re-serializes to itself byte-for-byte.** The regenerated file was produced by
  loading the 1.2 original through the new build and re-saving it, so the shipped file is exactly what
  the migration yields; the diff against the pre-change file is 85 lines — one `schemaVersion` and 83
  `"id": n`.
- The plan's four end-to-end steps, run outside the suite against the real file:
  1. `Validate(Error)` on `Example1.femex` is empty — and so is `Validate(Warning)`.
  2. `AssignMissingUids()` filled **392** objects; saved to a scratch path, reloaded, every uid came
     back identical, and the reloaded model still validates with no errors and no warnings — full
     coverage is silent, as designed.
  3. A second `AssignMissingUids()` on the reloaded model returned `0`: nothing was overwritten.
  4. The pre-change `Example1.femex` (schemaVersion 1.2, no load ids) loads with its 83 loads numbered
     1–83, reports the numbering and the 1.2 version, and raises no errors.

## Still open

Unchanged from the plan, and all five remain true of what was built:

- **`UnmappedMemberHandling` is still not set** on `FemexModel.JsonOptions`, so a 1.3 file read by a
  1.2 build drops its uids in silence — the exact failure mode review §4.5 calls disqualifying for an
  interchange format. Adjacent to this change and deserving its own pass; not folded in because it
  would turn every forward-compatible read into a throw, which is a policy decision of its own.
- **Robot's name-key is only half-served.** A warning tells an author their material has no name; it
  does not stop them shipping one.
- **`Parent ID` has no reader yet.** The moment FEMEX grows a splitting operation — a plate cut into
  several, a bar split at an intersection — it becomes real.
- **Nothing here tells a receiver what the uid *was*.** A translator holds the mapping from uid to its
  native `UniqueId` / GUID / label; the file does not. That is SAF's design and almost certainly right,
  but it means a uid is only as good as the exporter's memory of it.
- **Merging two FEMEX files is still not implemented**, only made possible. Integer ids still collide;
  a merge helper that keys on uid and remaps the integers around it is the obvious next step.
